# Log de Decisões Técnicas (ADR — Architecture Decision Records)

Registro de decisões técnicas relevantes do projeto, com data e motivo. Consulte antes de propor mudanças a algo já decidido aqui.

| Data | Decisão | Motivo |
|---|---|---|
| 2026-09-20 | Especificação técnica aprovada (ver `docs/SPEC.md`) | Baseline funcional/técnico do projeto |
| 2026-09-20 | Estrutura de repositório definida como monorepo `apps/` + `services/` + `packages/` (ver `docs/STRUCTURE.md`) | Alinhar com convenções reais de monorepos poliglotas (Turborepo/Nx-style); suportar TS/Python/Rust sem layout artificial; Docker opcional, não obrigatório |
| 2026-09-20 | `docs/diagrams/` reservado apenas para exports estáticos de diagramas (imagens/SVG), não para documentação em Markdown | Evitar confusão entre documentação canônica (`docs/*.md`) e artefatos gerados de diagramas |
| 2026-09-20 | `currentTime` de reprodução NÃO fica em estado do React (nem no Zustand) — só é lido sob demanda de `AudioEngine.getCurrentTime()`, dentro de `requestAnimationFrame` | Evitar 60 re-renders/segundo na árvore inteira; só o playhead (desenho direto no canvas) e o `TimeReadout` (throttled a 1x/segundo) leem esse valor — ver `docs/SPEC.md` §4.3 |
| 2026-09-20 | Paleta definida: fundo quase-preto `#0d0d10`, acento âmbar `#e2a63d` usado só em playhead/estado ativo | Evitar os clichês visuais de UI gerada por IA (terracota `#D97757`, preto puro `#0b0b0b`); acento único mantém o foco na waveform, conforme `docs/SPEC.md` §4.1 |
| 2026-09-20 | Time-stretch com preservação de pitch implementado como OLA simples (overlap-add), não WSOLA completo com alinhamento por correlação cruzada | Entrega a funcionalidade pedida (§4.3) com complexidade administrável; introduz leve "textura"/artefato perceptível em esticamentos extremos (perto de 0.25x ou 2.0x) — WSOLA com correlação é a evolução natural se a qualidade em extremos importar |
| 2026-09-20 | Loop no caminho nativo (`rate === 1`) usa `AudioBufferSourceNode.loop/loopStart/loopEnd` (sample-accurate, nativo do navegador); no caminho com `AudioWorklet` (`rate !== 1`), o loop é reimplementado manualmente dentro do processor | Web Audio não expõe loop nativo pra um `AudioWorkletNode` alimentado por dados brutos — a fonte de verdade da posição (`AudioContext.currentTime`) continua sendo a mesma em ambos os caminhos, então a UI não precisa saber qual caminho está ativo |
| 2026-09-20 | Sem testes automatizados para a lógica de DSP do `AudioWorklet` | `jsdom` (ambiente do Vitest) não implementa Web Audio API/AudioWorklet; validação é manual por ora — testes de navegador (Playwright) ficam como possível item de dívida técnica |
| 2026-09-21 | `play()` sempre chama `await context.resume()` antes de agendar qualquer fonte | Corrige bug relatado: após `pause()`, o navegador pode suspender o `AudioContext` (economia de energia); sem retomar explicitamente, o áudio ficava mudo até um `seek()` forçar um novo grafo. O relógio visual (baseado no próprio contexto) mascarava o problema, parecendo tocar normalmente |
| 2026-09-21 | `AudioEngine.setLoopRegion()` agora também define `loopEnabled` internamente (atômico), em vez da store chamar `setLoopRegion` + `setLoopEnabled` como duas operações separadas | Elimina uma janela de inconsistência onde a região podia ser aplicada com a flag de habilitação ainda desatualizada |
| 2026-09-21 | `seek()` e `setPlaybackRate()` agora resetam `this.state` para `"paused"` antes de chamar `play()` internamente pra reiniciar a fonte | Bug real encontrado via teste manual: `play()` tem uma guarda `if (this.state === "playing") return`; como essas duas funções paravam o áudio mas nunca tiravam o estado de `"playing"`, a chamada interna a `play()` era silenciosamente ignorada — o cursor visual continuava andando (calculado à parte), mas o áudio real nunca reiniciava, até um pause/play manual |
| 2026-09-21 | `getCurrentTime()` agora aplica o wrap do loop na própria fórmula do relógio (`raw % span` dentro da região) | O loop nativo do `AudioBufferSourceNode` volta o áudio sozinho, mas a fórmula do cursor era linear e não sabia disso — o som repetia corretamente, mas o cursor visual saía da região do loop, subindo indefinidamente |
| 2026-09-22 | `wasm-dsp` compilado com **AssemblyScript**, não Rust/C++ como `docs/STRUCTURE.md` originalmente descrevia | Sem toolchain Rust disponível no ambiente de build (sem `cargo`/`rustc`, e sem acesso de rede a `rust-lang.org` pra instalar via `rustup`). AssemblyScript compila 100% via npm/registry já liberado, produz um `.wasm` real (não um polyfill), com sintaxe próxima o bastante de TS pra qualquer LLM/dev futuro entender de cara. Migrar pra Rust depois é possível sem quebrar contrato — as funções exportadas (`analyzeFrames`, `classifyChords`, `estimateTempo`) podem ser reimplementadas em outra linguagem mantendo a mesma assinatura |
| 2026-09-22 | Chromagram calculado via FFT linear (mapeando bin→classe de altura), não uma CQT logarítmica de verdade | CQT real exige kernels espaçados geometricamente, bem mais complexo de implementar do zero; a aproximação por FFT é a técnica clássica usada por detectores de acorde "leves" e é suficiente pro Nível 1. A Camada 2 (servidor, Fase 4, via librosa/essentia) pode usar CQT de verdade — é justamente o que diferencia as duas camadas de precisão descritas no `SPEC.md` §4.4 |
| 2026-09-22 | Classificação de acordes por template matching (cosine similarity contra 36 templates fixos: 12 fundamentais × maior/menor/7ª dominante), sem modelo de ML treinado | Modelo CNN/CRNN treinado é explicitamente Camada 2 (servidor) no `SPEC.md` §4.4; o Nível 1 client-side pede "rápido, sempre ativo" com vocabulário simples — template matching roda em microsegundos e cobre exatamente o vocabulário pedido pra essa camada (maior/menor/7ª dominante) |
| 2026-09-22 | Suavização temporal do Nível 1 feita por filtro de moda (janela deslizante) + fusão de segmentos curtos, não um HMM/CRF de verdade | HMM/CRF com priors de transição musicalmente informados é explicitamente descrito como parte do pipeline completo (`SPEC.md` §4.4.3), mas roda melhor server-side (Camada 2, Fase 4) onde há mais tempo de processamento disponível; o filtro de moda é uma aproximação leve o bastante pro client-side não piscar frame-a-frame |
| 2026-09-22 | FFT/chroma/onset compartilham UMA passagem por frame (`analyzeFrames` retorna os dois num único array empacotado de 13 floats/frame), mas o cálculo é refeito do zero se `classifyChords`/`estimateTempo` forem chamados de novo | Evita duplicar a FFT entre chroma e onset (que são consumidos juntos, sempre); já é suficiente pra rodar em segundos num Web Worker pro tamanho de faixa esperado (até ~10min, NFR de performance do `SPEC.md` §5) |
| 2026-09-22 | Testes de sanidade da DSP (`wasm-dsp/smoke-test.mjs`) usam áudio sintético (senoides, acordes, cliques de metrônomo) rodando via `node`, fora do `npm test` do monorepo | Vitest/jsdom não instanciam WASM+ESM do jeito que o navegador faz; rodar via Node puro (mesmo runtime usado pelo `asc`) é mais simples e ainda assim valida a matemática (FFT, chroma, classificação, autocorrelação) de ponta a ponta antes de integrar com a UI |
| 2026-09-23 | `apps/web/nginx.conf` adiciona mapeamento explícito de `.wasm` → `application/wasm`; `analysis-worker.js` importa o módulo WASM dinamicamente (dentro do handler, não estático no topo do arquivo); `analyzeTrack()` no client tem timeout de 20s | Bug real: `WebAssembly.compileStreaming()` (usado pelo glue gerado pelo AssemblyScript) exige `Content-Type: application/wasm` exato; sem isso, falha, e como o import do módulo era estático, a falha matava a avaliação do worker inteiro SEM disparar erro nenhum visível — `self.onmessage` nunca era registrado, e a análise ficava "Analisando…" pra sempre, sem nunca resolver nem rejeitar a Promise. As três mudanças juntas resolvem a causa raiz (MIME) e adicionam duas camadas de defesa (import dinâmico + timeout) pra qualquer falha futura similar aparecer como erro visível em vez de travar silenciosamente |
| 2026-09-24 | **Correção da entrada acima:** `apps/web/nginx.conf` foi **removido**; o mapeamento de `.wasm` NÃO era necessário | Testado com Nginx real (não só suposição): a tabela `mime.types` padrão já inclui `application/wasm` há alguns anos, tanto na imagem `nginx:alpine` quanto na distribuição usada pra testar aqui. Meu `types { application/wasm wasm; }` customizado tinha um bug próprio — em Nginx, declarar um bloco `types {}` num contexto (server) **substitui inteiramente** a tabela herdada do contexto pai (http), em vez de só adicionar uma entrada; isso quebrou `.html`/`.js`/`.css` (passaram a ser servidos como texto puro, causando o "aparece o HTML cru na tela" relatado). O import dinâmico + timeout do worker continuam válidos e foram mantidos — só a parte do Nginx foi revertida |
